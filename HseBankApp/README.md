# HSEBankApp

## 1. Общая информация

**HSEBankApp** — это консольное приложение для управления банковскими счетами и операциями. Оно позволяет пользователям:

1. Создавать и управлять банковскими счетами пользователей.

2. Добавлять и удалять финансовые операции для банковских счетов пользователя.

3. Добавление новых категорий операций.

4. Управлять банковскими счетами пользователя.

5. Приложение построено на основе принципов SOLID, GRASP и паттернов проектирования, что делает его гибким, расширяемым и поддерживаемым.

## 2. Принципы SOLID и GRASP

### S - Single Responsibility Principle (Принцип единственной ответственности)

1. Каждый класс выполняет только одну задачу:

    - User отвечает за управление данными пользователя.

    - BankAccount управляет банковскими счетами.

    - FinancialService отвечает за бизнес-логику операций.

    - OperationDataAccess отвечает за доступ к данным операций.

### O - Open/Closed Principle (Принцип открытости/закрытости)

1. Категории операций (Category) могут быть расширены без изменения кода.

2. Реализован интерфейсный слой (I*DataAccess), что позволяет заменить реализацию хранилища данных без изменения бизнес-логики.

### L - Liskov Substitution Principle (Принцип подстановки Барбары Лисков)

1. Все реализации IDataAccess могут заменять друг друга без изменения кода.

### I - Interface Segregation Principle (Принцип разделения интерфейсов)

1. Интерфейсы для доступа к данным (IBankAccountDataAccess, ICategoryDataAccess) разделены, чтобы классы зависели только от нужных методов.

### D - Dependency Inversion Principle (Принцип инверсии зависимостей)

1. FinancialService зависит от интерфейсов IOperationDataAccess и IBankAccountDataAccess, а не от конкретных реализаций.

### GRASP 

- Controller — FinancialService управляет бизнес-логикой.

- Creator — классы User, BankAccount, Operation создают объекты инициализации.

- Low Coupling — слои Domain, Infrastructure и Application слабо связаны.

- High Cohesion — классы логически связаны с выполняемыми функциями.

## 3. Используемые паттерны проектирования

### 1. Singleton (Одиночка)

Используется в BankAccountDataAccess, CategoryDataAccess, UserDataAccess, OperationDataAccess.

Зачем? Гарантирует наличие единственного экземпляра класса доступа к данным в памяти.

### 2. Repository (Репозиторий)

IOperationDataAccess, IBankAccountDataAccess обеспечивают единообразный доступ к данным.

Зачем? Отделяет бизнес-логику от работы с базой данных.

### 3. Factory Method (Фабричный метод)

Реализуется в создании Operation, Category, User.

Зачем? Позволяет создавать объекты, скрывая сложную логику создания.

### 4. Dependency Injection (Внедрение зависимостей)

Используется для передачи IOperationDataAccess, IBankAccountDataAccess в FinancialService через конструктор.

Зачем? Позволяет легко заменять реализации и упрощает тестирование.

Где? В FinancialService, который получает зависимости через конструктор (инверсированное управление зависимостями).
